# إعداد الحسابات الحقيقية في همسات

هذه المرحلة تضيف أساس تسجيل الدخول عبر Supabase، لكنها لا تصبح فعالة قبل إنشاء مشروع Supabase وإضافة إعداداته وتطبيق ترحيل قاعدة البيانات.

## 1) إنشاء المشروع
1. افتحي https://supabase.com/dashboard وأنشئي مشروعًا جديدًا.
2. اختاري كلمة مرور قوية لقاعدة البيانات واحتفظي بها في مكان آمن.
3. من Project Settings ثم API انسخي Project URL وPublishable key (أو anon key القديم).
4. لا تنسخي service_role أو Secret key إلى ملفات الواجهة أو GitHub أو المحادثة.

## 2) إعداد ملفات المشروع
1. انسخي `supabase/config.example.js` إلى `supabase/config.js`.
2. ضعي Project URL والمفتاح العام فقط في الملف الجديد.
3. لا ترفعي `config.js` إلى GitHub؛ أضيفيه إلى .gitignore.
4. **لا تشغّلي ملفات migrations القديمة بشكل أعمى على مشروع موجود فيه جداول وبيانات.** في مشروع Hamsat الحالي كان سجل Supabase migrations فارغًا رغم وجود جداول وبيانات فعلية. تم لاحقًا تسجيل migrations `0015` و`0016` و`0017` في سجل المشروع. لا يزال سجل migrations لا يثبت أن `0001` إلى `0014` طُبقت عبر نظام migrations؛ لذلك لا تشغّلي هذه الملفات القديمة على قاعدة موجودة، وراجعي المخطط وخذي نسخة احتياطية قبل أي تعديل.
5. إذا كان المشروع جديدًا تمامًا وفارغًا، اتبعي ملفات migrations بالترتيب الرقمي من `0001` إلى `0010` بعد مراجعتها.
6. إذا كان المشروع الحالي الذي يحتوي بيانات Hamsat، راجعي `0010_room_policy_and_trigger_hardening.sql` كترحيل إصلاح مستقل، وتأكدي من وجود الجداول المطلوبة قبل تطبيقه. لا تشغّليه على Production قبل النسخ الاحتياطي ومراجعة الأثر.

## 3) إعداد تسجيل البريد
- Authentication ثم URL Configuration: أضيفي رابط همسات المنشور إلى Site URL وRedirect URLs.
- Authentication ثم Providers: فعّلي Email.
- اختاري هل تريدين تأكيد البريد قبل السماح بالدخول (موصى به).
- اضبطي SMTP موثوقًا قبل الإطلاق العام؛ إعداد البريد الافتراضي قد يكون محدودًا.

## 4) إعداد الهاتف
- فعّلي Phone provider.
- اربطي مزود SMS مدعومًا من Supabase وأدخلي بياناته داخل لوحة Supabase فقط.
- حددي دولة الجزائر ورمزها الدولي +213 في تجربة الأرقام.
- لا يمكن إرسال OTP حقيقي قبل إعداد مزود SMS والتحقق من رصيده/حدوده.

## 5) اختبار آمن
- أنشئي حساب اختبار ببريد تملكينه.
- اختبري تأكيد البريد، تسجيل الدخول، تسجيل الخروج، واستعادة كلمة المرور.
- اختبري OTP على رقم تملكينه فقط.
- لا تستخدمي بيانات حقيقية للزوار قبل إكمال اختبار صلاحيات API وربط ملف المستخدم بالخادم.

## متطلبات الصوت المباشر
- يجب أن تكون بنية الغرف والمقاعد والسياسات متوافقة مع migrations `0005` و`0009` و`0010`.
- يجب تفعيل Supabase Realtime في المشروع؛ تضيف migrations `0005` و`0009` و`0010` جداول الرسائل والأعضاء والمقاعد إلى `supabase_realtime`.
- محرك الصوت الحالي WebRTC بنمط P2P ويستخدم STUN عام فقط. قبل الإطلاق العام، أضيفي TURN أو استخدمي SFU مُدارًا مع بيانات اتصال قصيرة العمر يصدرها خادم موثوق.
- اختبري حسابين على هاتفين حقيقيين، مع السماح بالميكروفون والصوت، ثم أعيدي الاختبار على شبكتين مختلفتين.

## ما لا تزال هذه المرحلة لا تنفذه
- لا تعتبر الصوت الجماعي موثوقًا حتى إعداد TURN أو SFU واختباره على شبكات مختلفة.
- تم تطبيق migrations `0015` و`0016` و`0017` و`0018` في قاعدة بيانات المشروع لإنشاء الرسائل الخاصة والإشعارات ومنح صلاحيات Data API محدودة مع بقاء RLS مفعّلاً، ونقل تنفيذ RPC ذي الصلاحيات المرتفعة إلى schema غير مكشوفة. ما زال يلزم اختبار المراسلة بين حسابين فعليين. الألعاب الجماعية والوكالات ولوحة الإدارة الشاملة تحتاج إلى استكمال واختبار منفصلين.
- لا تضعي مفاتيح الخدمة السرية في المتصفح.
